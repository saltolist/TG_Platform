> Модель retrieval (граф, каскад L0/L1/L2, инструменты, принцип
> read-tools/write-tools) зафиксирована в [ADR-008](adr/008-agentic-graph-rag.md).

## Порядок приоритетов

| Приоритет | Что | Статус |
|---|---|---|
| **1** | Agentic RAG: чтение постов, заметок, их вложений и комментариев по необходимости | ⏳ План |
| **2** | Агентные действия над постами (правка / отложить / опубликовать) | ⏳ План |
| **3** | Аналитические (агрегирующие) запросы по всему каналу | 💭 Предпосылки не заложены |
| Отложено | Ответ на комментарии по приказу пользователя | 💭 Не в этом цикле |

## Приоритет 1 — Agentic RAG: посты, заметки, вложения, комментарии (чтение)

**Цель:** AI при ответе (global и post chat) может при необходимости подтянуть
текст и медиа постов, заметки к ним, вложенные в заметки файлы/медиа, а также
**прочитать комментарии поста**, если это нужно для ответа — без ручного
перечисления всего этого в каждом запросе.

Чтение комментариев (`ListPostComments`) — часть Приоритета 1 наравне с постами и
заметками. Отложена только **работа** с комментариями от имени пользователя —
ответ на них по команде (см. [Отложено](#отложено--ответ-на-комментарии)).

**Явная граница:** Приоритет 1 — это «найти релевантное (единицы явно
определяемых кандидатов) и раскрыть детали», а не агрегация по всему каналу.
«Дай посты с самыми негативными комментариями» или «сколько раз упоминали X» —
не решается agentic-циклом, это отдельное направление, см.
[Приоритет 3](#приоритет-3--аналитические-агрегирующие-запросы).

### Индексация (запись)

- [ ] `post_text` — текст поста в общий текстовый индекс (расширение текущего
      `note_embeddings` / pgvector-контура).
- [ ] `attachment_text` — извлечение текста из вложений заметок (PDF/doc), где это
      дёшево на этапе записи.
- [ ] `media_meta` — имя/alt/подпись медиа постов и заметок (без бинарника).
- [ ] Существующая индексация заметок (`note_chunk`) не меняется по формату,
      только становится частью общего индекса узлов.

### Retrieval — каскад

- [ ] **L0** — правила пропуска RAG (реплики без предметного вопроса, правки
      стиля/тона, уже покрытые bundle).
- [ ] **L1** — flat hybrid retrieval по умолчанию: один embed запроса
      (history-expansion + rewrite-on-miss, как сейчас) → vector search по
      `post_text` + `note_chunk` + `attachment_text` → `format_rag_context`.
      Без обхода графа, без vision.
- [ ] **Sufficiency-check вместо miss-detection** — эскалация проверяется после
      **каждого** L1-результата, а не только при пустом ответе (высокая similarity
      не означает достаточность контекста). Ярус A (эвристики, без LLM):
      - [ ] Промах (пусто / similarity ниже порога) — как сегодня в `rag_query.py`.
      - [ ] Непройденный сосед с прямой ссылкой в самом чанке — хранить рядом с
            чанком список referenced `attachment:<id>` отдельно от очищенного
            текста индекса.
      - [ ] Текстовые маркеры-указатели («см.», «подробнее в», «результаты в
            файле») + непройденный сосед по манифесту.
      - [ ] Несоответствие типа ожидаемого ответа контенту чанка (вопрос ждёт
            цифры — в чанке нет цифр; вопрос про визуал — контент текстовый).
      - [ ] Слишком короткий/teaser-чанк относительно среднего размера.
      - [ ] Follow-up по истории (ссылка на ранее открытый узел вне контекста).
      Ярус B (только если Ярус A неоднозначен) — короткий structured-запрос к
      `ragReasonerModels` с манифестом непройденных структурных соседей (id +
      type + заголовок/имя, без содержимого) → `{sufficient, open_next}`.
- [ ] **Манифест структурных соседей** — бесплатное чтение `len()`/заголовков
      уже загруженного JSONB поста/заметки (`notes`, `media`, `comments`,
      `files`) для передачи planner'у; не текстовый поиск ссылок — граф
      реализован как вложенность (containment), не как ссылки между документами.
- [ ] **L2** — agentic-цикл по эскалации. Инструменты (read-only, вызываются
      planner'ом автономно):
      - [ ] `SearchNodes(scope, query, node_types)`
      - [ ] `OpenPost(post_id)` — весь JSONB поста одним запросом
      - [ ] `ListPostNotes(post_id)`
      - [ ] `OpenNote(note_id)`
      - [ ] `ListNoteAttachments(note_id)`
      - [ ] `HydrateAttachment(ref, mode)` — `metadata | text | vision`, см.
            ниже про стоимость и кэш
      - [ ] `ListPostComments(post_id)` — комментарии поста, читается лениво из
            уже загруженного JSONB, без отдельного embedding-индекса
      - [ ] `Stop(reason)`
- [ ] **Гидратация вложений — стоимость и кэш:**
      - [ ] `text`: write-time извлечение PDF/doc через ту же очередь, что и
            индексация заметок (`rag_worker.py`); lazy-fallback с кэшированием
            результата обратно в `attachment_text`, если write-time ещё не
            прошёл.
      - [ ] `vision`: всегда реальный вызов `visionModels`; кэш по хэшу
            содержимого файла (не по `url`); не дублировать vision для файла,
            уже найденного через `attachment_text`.
- [ ] **Отказоустойчивость** — сбой гидратации (файл не скачался, нет ключа
      vision-модели) не должен ронять запрос: fail-soft (лог + пропуск
      источника), по аналогии с текущим `try/except` вокруг RAG в `ai.py`.
      System prompt ответной модели явно требует не галлюцинировать факты при
      неполном контексте, а сообщать, что не найдено.
- [ ] Лимиты: `RAG_AGENT_MAX_STEPS`, `RAG_AGENT_MAX_VISION`, `visited: set(ref)`.
- [ ] `ragReasonerModels` получает роль planner'а agentic-цикла и Ярус-B
      sufficiency-проверки (в дополнение к текущему rewrite-on-miss).
- [ ] Конфиг: `RAG_MODE=off|flat|agentic|auto`, `RAG_ESCALATE_MIN_SIMILARITY`,
      `RAG_ESCALATE_ON_MISS`.
- [ ] Точка входа не меняется: каскад запускается синхронно внутри
      `POST /ai/reply/`, при тех же гейтах, что и сегодняшний RAG
      (`RAG_ENABLED=1` + реальная LLM, не заглушка).

### Критерий завершения этапа

- В global chat AI может найти и процитировать релевантный **пост** (не только
  заметку), не имея его в bundle.
- Вопрос про содержимое вложения заметки (PDF/таблица) даёт ответ по факту из
  файла, а не только по названию/alt.
- Вопрос про картинку в посте/заметке приводит к vision-гидратации **только**
  когда это релевантно вопросу — обычные текстовые вопросы не тянут vision.
- Вопрос про реакцию аудитории/комментарии к посту («что пишут в комментариях»,
  «есть негатив?») приводит к чтению комментариев через `ListPostComments`, не
  требуя от пользователя открывать пост вручную.
- Большинство запросов (без явной потребности в медиа/вложениях/комментариях)
  укладываются в L0/L1 — agentic-цикл не добавляет задержку там, где не нужен.

## Приоритет 2 — Агентные действия над постами

**Цель:** AI может по явной команде пользователя в чате отредактировать,
отложить или опубликовать пост — не только читать данные, но и менять их.

Реализуется **после** Приоритета 1, так как переиспользует те же read-tools
(`OpenPost` и т.д.) для того, чтобы агент понимал текущее состояние поста перед
правкой.

### Write-tools (обёртка над существующими эндпоинтами)

- [ ] `ProposeEditPost(post_id, patch)` — поверх `PATCH /posts/{post_id}/`.
- [ ] `SchedulePost(post_id, scheduled_at)` — поверх `POST /posts/{post_id}/schedule/`.
- [ ] `PublishPost(post_id)` — поверх `POST /posts/{post_id}/publish/`.

### Обязательный принцип (зафиксирован в ADR-008, не подлежит пересмотру без нового ADR)

Write-tools вызываются **только** по явной команде пользователя в конкретном
сообщении (не автономно по инициативе planner'а) и требуют **подтверждения перед
применением** — черновик правки/расписания/публикации показывается пользователю,
фактическое действие в Telegram выполняется только после подтверждения. Read-tools
из Приоритета 1 планировщик вызывает автономно; write-tools — нет.

### Открытые вопросы для проектирования (до начала реализации)

- [ ] Формат превью правки в UI чата (карточка diff перед применением).
- [ ] Что происходит при истечении/отмене черновика правки (TTL, явная отмена).
- [ ] Нужно ли различать «предложить правку» и «применить правку» как два разных
      сообщения пользователя, или подтверждение — это отдельный UI-контрол.

### Критерий завершения этапа

- Пользователь может попросить AI отредактировать пост в чате, увидеть
  предложенную правку и явно подтвердить её применение.
- Отложить/опубликовать пост через AI работает только после подтверждения,
  ошибки Telegram-синхронизации (как и в ручном flow) не проглатываются молча.

## Приоритет 3 — аналитические (агрегирующие) запросы

**Цель:** закрыть вопросы вида «дай посты с самыми негативными комментариями»,
«сколько раз упоминали X», «средняя вовлечённость за месяц» — которые требуют
**агрегации по всему каналу**, а не поиска релевантного фрагмента. Явно вне
периметра [ADR-008](adr/008-agentic-graph-rag.md#границы-модели-что-agentic-rag-не-решает):
это не расширение agentic-цикла, а отдельный класс инструментов.

**Почему не через agentic RAG:** `SearchNodes` ищет top-k **похожих по смыслу**
на текст запроса; у «негативности» или «количества упоминаний» нет текста для
сравнения embedding'ом — это вычисляемые признаки, требующие прохода по **всем**
постам/комментариям и `GROUP BY`/`ORDER BY`, а не similarity search. Даже без
агрегации простой перебор десятков постов не помещается в
`RAG_AGENT_MAX_STEPS`.

### Предпосылки (write-time, до появления инструментов)

- [ ] **Precomputed тональность комментариев** — классификация (правило /
      дешёвая модель / LLM) выполняется при синхронизации комментариев из
      Telegram (`comments_flow.py` / `comment_sync_pending.py`), результат
      сохраняется как поле на комментарии. Не в момент запроса.
- [ ] Стоимость пересчёта при backfill старых комментариев — отдельный вопрос
      проектирования (разовая миграция vs постепенный пересчёт).
- [ ] Место хранения — поле в JSON комментария на посте vs отдельная таблица
      (зависит от того, понадобятся ли по этому полю отдельные индексы/выборки).

### Инструменты (аналитические, отдельная категория — не read-tools retrieval)

- [ ] `RankPostsByNegativeComments(limit)` — прямой SQL `GROUP BY`/`ORDER BY` по
      precomputed `sentiment`, не vector search и не agentic-цикл.
- [ ] Общий принцип: агрегирующий вопрос → структурный SQL-запрос по
      precomputed полю, а не проход agentic-цикла по многим объектам.

### Связь с существующей аналитикой

Та же схема, что уже используется в продукте для числовых метрик постов
(просмотры/репосты/реакции — `backend/app/services/analytics/`) — это
расширение существующего аналитического контура добавлением ещё одной
precomputed-метрики (тональность), а не новая архитектура.

### Критерий завершения этапа

- Пользователь может спросить «какие посты вызвали больше всего негатива в
  комментариях» и получить осмысленный ранжированный список без прохода
  agentic-цикла по каждому посту канала.
- Агрегирующие вопросы не расходуют бюджет `RAG_AGENT_MAX_STEPS` — они идут
  отдельным, более дешёвым путём (один SQL-запрос).

## Отложено — ответ на комментарии

Осознанно вынесено за пределы текущих приоритетов. Речь только о **записи**
(ответе от AI в комментарии) — чтение комментариев решено в Приоритете 1 и от
этого пункта не зависит.

- [ ] **Ответ на комментарии по приказу пользователя** — статус: под вопросом,
      окончательно не решено, будет реализовано только если появится чёткая
      необходимость. Если будет реализовано — write-tool с тем же принципом
      подтверждения, что и для постов (Приоритет 2), выключен по умолчанию за
      отдельным флагом.
