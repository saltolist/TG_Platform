## Порядок приоритетов

| Приоритет | Что | Статус |
|---|---|---|
| **1** | Agentic RAG: чтение постов, заметок, их вложений и комментариев по необходимости | ⏳ План |
| **2** | Агентные действия над постами (правка / отложить / опубликовать) | ⏳ План |
| **3** | Аналитические (агрегирующие) запросы по всему каналу | 💭 Предпосылки не заложены |
| Отложено | Ответ на комментарии по приказу пользователя | 💭 Не в этом цикле |

## Приоритет 1 — Agentic RAG: посты, заметки, вложения, комментарии (чтение)

**Цель:** AI при ответе (global и post chat) может при необходимости подтянуть
текст и медиа постов, заметки к ним, вложенные в заметки файлы/медиа, а также
**прочитать комментарии поста**, если это нужно для ответа — без ручного
перечисления всего этого в каждом запросе.

Чтение комментариев (`ListPostComments`) — часть Приоритета 1 наравне с постами и
заметками. Отложена только **работа** с комментариями от имени пользователя —
ответ на них по команде (см. [Отложено](#отложено--ответ-на-комментарии)).

**Явная граница:** Приоритет 1 — это «найти релевантное (единицы явно
определяемых кандидатов) и раскрыть детали», а не агрегация по всему каналу.
«Дай посты с самыми негативными комментариями» или «сколько раз упоминали X» —
не решается agentic-циклом, это отдельное направление, см.
[Приоритет 3](#приоритет-3--аналитические-агрегирующие-запросы).

Шаги ниже упорядочены по зависимостям и сдаются последовательными приростами
(по аналогии с «Шаг N» в [phase-2-ai.md](../backend/phases/phase-2-ai.md)):
каждый шаг опирается только на то, что реализовано в предыдущих.

### Шаг 1.1 — Индексация (запись) + L1 на расширенном индексе

**Затрагивает:** `rag.py`, `rag_worker.py` (индексация); существующий
`retrieve_rag_for_reply` (поиск) — без нового agentic-кода.

- [ ] `post_text` — текст поста в общий текстовый индекс (расширение текущего
      `note_embeddings` / pgvector-контура).
- [ ] `attachment_text` — извлечение текста из вложений заметок (PDF/doc), где это
      дёшево на этапе записи.
- [ ] `media_meta` — имя/alt/подпись медиа постов и заметок (без бинарника).
- [ ] Существующая индексация заметок (`note_chunk`) не меняется по формату,
      только становится частью общего индекса узлов.
- [ ] **L1** начинает искать по расширенному индексу: один embed запроса
      (history-expansion + rewrite-on-miss, как сейчас) → vector search по
      `post_text` + `note_chunk` + `attachment_text` → `format_rag_context`.
      Без обхода графа, без vision.

Уже самостоятельный прирост: без единой строчки agentic-кода AI начинает
находить и цитировать посты и текст вложений, а не только заметки.

### Шаг 1.2 — L0: правила пропуска RAG

Независим от остальных шагов, можно делать в любой момент.

- [ ] реплики без предметного вопроса
- [ ] правки стиля/тона
- [ ] уже покрытые bundle

### Шаг 1.3 — Манифест структурных соседей + Ярус A (fast-path + признаки)

Зависит от Шага 1.1 (признаки опираются на `referenced attachment:<id>` и
`media_meta`, появляющиеся при индексации).

Ярус A **не решает**, нужен ли Ярус B — эта развилка сама была ненадёжной
эвристикой (см. [ADR-008](adr/008-agentic-graph-rag.md#условия-эскалации-l1--l2-проверка-достаточности-а-не-только-промах)).
Роль Яруса A — только два fast-path случая, где ответ уже известен без LLM, и
поставка признаков для Яруса B во всех остальных случаях.

- [ ] **Манифест структурных соседей** — бесплатное чтение `len()`/заголовков
      уже загруженного JSONB поста/заметки (`notes`, `media`, `comments`,
      `files`) для передачи planner'у; не текстовый поиск ссылок — граф
      реализован как вложенность (containment), не как ссылки между документами.
- [ ] Fast-path 1 — **промах** (пусто / similarity ниже порога, как сегодня в
      `rag_query.py`) → эскалация без Яруса B, оценивать нечего.
- [ ] Fast-path 2 — **непройденный сосед с прямой ссылкой в самом чанке**
      (хранить рядом с чанком список referenced `attachment:<id>` отдельно от
      очищенного текста индекса) → эскалация с уже известной целью, без
      Яруса B.
- [ ] Признаки для Яруса B (не эскалируют сами по себе, передаются в
      structured-запрос reasoner'у):
      - [ ] `pointer_phrase` — текстовые маркеры-указатели («см.», «подробнее
            в», «результаты в файле»).
      - [ ] `answer_type_mismatch` — несоответствие типа ожидаемого ответа
            контенту чанка (вопрос ждёт цифры — в чанке нет цифр; вопрос про
            визуал — контент текстовый).
      - [ ] `chunk_too_short` — слишком короткий/teaser-чанк относительно
            среднего размера.
      - [ ] `is_followup` — follow-up по истории (ссылка на ранее открытый
            узел вне контекста).
- [ ] Конфиг порогов: `RAG_ESCALATE_MIN_SIMILARITY`, `RAG_ESCALATE_ON_MISS`.

### Шаг 1.4 — Ярус B: LLM-проверка достаточности (вызывается почти всегда)

Зависит от Шага 1.3 (нужны манифест и признаки).

- [ ] Вызывается для **всех** L1-результатов, кроме двух fast-path из Шага 1.3
      (промах, известная ссылка) — не «только если неоднозначно», см.
      обоснование в [ADR-008](adr/008-agentic-graph-rag.md#условия-эскалации-l1--l2-проверка-достаточности-а-не-только-промах).
- [ ] Короткий structured-запрос к `ragReasonerModels` с признаками Яруса A
      (`pointer_phrase`, `answer_type_mismatch`, `chunk_too_short`,
      `is_followup`) и манифестом непройденных структурных соседей (id + type
      + заголовок/имя, без содержимого) → `{sufficient, open_next}`.
- [ ] `ragReasonerModels` получает роль Яруса-B проверки в дополнение к
      текущему rewrite-on-miss.
- [ ] Без настроенной RAG Reasoner-модели Ярус B недоступен — degraded-режим:
      работает только L1 + fast-path Яруса A, без признаков 3–6.

### Шаг 1.5 — L2: agentic-цикл и базовые read-инструменты

Зависит от Шагов 1.3–1.4 (нужен триггер эскалации) и от Шага 1.1 (индекс для
`SearchNodes`).

**Затрагивает:** новые `rag_agent.py` (цикл/planner), `rag_tools.py`
(инструменты) — существующий `retrieve_rag_for_reply` остаётся точкой входа
для L1, не заменяется.

- [ ] `SearchNodes(scope, query, node_types)`
- [ ] `OpenPost(post_id)` — весь JSONB поста одним запросом
- [ ] `ListPostNotes(post_id)`
- [ ] `OpenNote(note_id)`
- [ ] `ListNoteAttachments(note_id)`
- [ ] `Stop(reason)`
- [ ] Лимиты: `RAG_AGENT_MAX_STEPS`, `visited: set(ref)`.
- [ ] Конфиг: `RAG_MODE=off|flat|agentic|auto`.
- [ ] Точка входа не меняется: каскад запускается синхронно внутри
      `POST /ai/reply/`, при тех же гейтах, что и сегодняшний RAG
      (`RAG_ENABLED=1` + реальная LLM, не заглушка).

На этом шаге L2 уже полноценно ходит по вложенности пост → заметки → метаданные
вложений (без чтения бинарного содержимого). `HydrateAttachment` и
`ListPostComments` добавляются следующими шагами как новые инструменты в тот
же цикл.

### Шаг 1.6 — Гидратация вложений: text

Зависит от Шага 1.5 (цикл и набор инструментов уже существуют, добавляется
ещё один инструмент).

- [ ] `HydrateAttachment(ref, mode="text")`: write-time извлечение PDF/doc
      через ту же очередь, что и индексация заметок (`rag_worker.py`).
- [ ] Lazy-fallback с кэшированием результата обратно в `attachment_text`,
      если write-time ещё не прошёл.

### Шаг 1.7 — Гидратация вложений: vision

Зависит от Шага 1.6 (тот же инструмент `HydrateAttachment`, второй режим);
может делаться сразу после или параллельно другим шагом.

- [ ] `HydrateAttachment(ref, mode="vision")`: всегда реальный вызов
      `visionModels`.
- [ ] Лимит `RAG_AGENT_MAX_VISION`.
- [ ] Кэш по хэшу содержимого файла (не по `url`).
- [ ] Не дублировать vision для файла, уже найденного через `attachment_text`.

### Шаг 1.8 — Чтение комментариев поста

Зависит только от Шага 1.5 (цикл уже существует); независим от Шагов 1.6/1.7,
можно делать параллельно.

- [ ] `ListPostComments(post_id)` — комментарии поста, читается лениво из уже
      загруженного JSONB, без отдельного embedding-индекса.

### Шаг 1.9 — Отказоустойчивость

Зависит от Шагов 1.5–1.8 (нужны реальные точки отказа: гидратация, бюджет
шагов).

- [ ] Сбой гидратации (файл не скачался, нет ключа vision-модели) не должен
      ронять запрос: fail-soft (лог + пропуск источника), по аналогии с
      текущим `try/except` вокруг RAG в `ai.py`.
- [ ] System prompt ответной модели явно требует не галлюцинировать факты при
      неполном контексте, а сообщать, что не найдено.

### Шаг 1.10 — Intent-роутинг на аналитику поста

Зависит от Шага 1.5 только для global chat-ветки (использует тот же L2-цикл,
когда пост нужно сначала найти по содержимому); для post chat-ветки `post_id`
уже известен из контекста чата, L2 не требуется вовсе. Независим от Шагов
1.6–1.9. Модель описана в
[ADR-008](adr/008-agentic-graph-rag.md#аналитика-поста-и-канала-числовой-контекст-а-не-текстовый-узел).

- [ ] Rule-based классификатор intent'а (`content` | `post_analytics` |
      `channel_analytics`) — до эмбеддинга вопроса, без LLM.
- [ ] `GetPostAnalytics(post_id, period)` — обёртка над
      `services/analytics/post_metrics.build_post_trend`.
- [ ] Post chat: `post_analytics` intent вызывает тул напрямую, минуя
      L0/L1/L2 текстового каскада для этого сообщения.
- [ ] Global chat: `post_analytics` intent сначала идентифицирует пост через
      обычный `SearchNodes`/L1, затем вызывает `GetPostAnalytics` как L2-шаг.
- [ ] Разбор периода из формулировки вопроса («за неделю» → `7d`) с фолбэком
      на дефолт (`30d`), по значениям `channel_metrics.VALID_PERIODS`.
- [ ] Исход `channel_analytics` того же классификатора маршрутизируется в
      [Приоритет 3](#приоритет-3--аналитические-агрегирующие-запросы) —
      реализуется вместе с ним, не здесь.

### Критерий завершения этапа

- В global chat AI может найти и процитировать релевантный **пост** (не только
  заметку), не имея его в bundle.
- Вопрос про содержимое вложения заметки (PDF/таблица) даёт ответ по факту из
  файла, а не только по названию/alt.
- Вопрос про картинку в посте/заметке приводит к vision-гидратации **только**
  когда это релевантно вопросу — обычные текстовые вопросы не тянут vision.
- Вопрос про реакцию аудитории/комментарии к посту («что пишут в комментариях»,
  «есть негатив?») приводит к чтению комментариев через `ListPostComments`, не
  требуя от пользователя открывать пост вручную.
- Вопрос про производительность поста («сколько просмотров», «как зашёл пост»)
  отвечается через `GetPostAnalytics`, минуя текстовый RAG целиком.
- Большинство запросов (без явной потребности в медиа/вложениях/комментариях/
  аналитике) укладываются в L0/L1 — agentic-цикл не добавляет задержку там,
  где не нужен.

## Приоритет 2 — Агентные действия над постами

**Цель:** AI может по явной команде пользователя в чате отредактировать,
отложить или опубликовать пост — не только читать данные, но и менять их.

Реализуется **после** Приоритета 1, так как переиспользует те же read-tools
(`OpenPost` и т.д.) для того, чтобы агент понимал текущее состояние поста перед
правкой.

### Write-tools (обёртка над существующими эндпоинтами)

- [ ] `ProposeEditPost(post_id, patch)` — поверх `PATCH /posts/{post_id}/`.
- [ ] `SchedulePost(post_id, scheduled_at)` — поверх `POST /posts/{post_id}/schedule/`.
- [ ] `PublishPost(post_id)` — поверх `POST /posts/{post_id}/publish/`.

### Обязательный принцип (зафиксирован в ADR-008, не подлежит пересмотру без нового ADR)

Write-tools вызываются **только** по явной команде пользователя в конкретном
сообщении (не автономно по инициативе planner'а) и требуют **подтверждения перед
применением** — черновик правки/расписания/публикации показывается пользователю,
фактическое действие в Telegram выполняется только после подтверждения. Read-tools
из Приоритета 1 планировщик вызывает автономно; write-tools — нет.

### Открытые вопросы для проектирования (до начала реализации)

- [ ] Формат превью правки в UI чата (карточка diff перед применением).
- [ ] Что происходит при истечении/отмене черновика правки (TTL, явная отмена).
- [ ] Нужно ли различать «предложить правку» и «применить правку» как два разных
      сообщения пользователя, или подтверждение — это отдельный UI-контрол.

### Критерий завершения этапа

- Пользователь может попросить AI отредактировать пост в чате, увидеть
  предложенную правку и явно подтвердить её применение.
- Отложить/опубликовать пост через AI работает только после подтверждения,
  ошибки Telegram-синхронизации (как и в ручном flow) не проглатываются молча.

## Приоритет 3 — аналитические (агрегирующие) запросы

**Цель:** закрыть вопросы вида «как растёт канал», «топ постов за месяц», «дай
посты с самыми негативными комментариями», «средняя вовлечённость за месяц» —
которые требуют **агрегации по всему каналу**, а не поиска релевантного
фрагмента. Явно вне периметра
[ADR-008](adr/008-agentic-graph-rag.md#границы-модели-что-agentic-rag-не-решает):
это не расширение agentic-цикла, а отдельный класс инструментов.

**Почему не через agentic RAG:** `SearchNodes` ищет top-k **похожих по смыслу**
на текст запроса; у «негативности», «количества упоминаний» или «динамики
канала» нет текста для сравнения embedding'ом — это вычисляемые признаки,
требующие прохода по **всем** постам/комментариям и `GROUP BY`/`ORDER BY`, а не
similarity search. Даже без агрегации простой перебор десятков постов не
помещается в `RAG_AGENT_MAX_STEPS`.

Приоритет состоит из двух независимых частей — по готовности данных они не
равны: канал-аналитика ниже не требует нового precompute вообще, тональность
комментариев требует.

### Шаг 3.1 — Аналитика канала (без нового precompute, обёртка над готовым)

Данные уже посчитаны и хранятся: `ChannelMetricSnapshot`/`PostMetricSnapshot`,
регулярный snapshot-cron (`analytics_snapshot.py`). Самый дешёвый пункт этого
приоритета — не нужен новый этап записи, только обёртка существующих функций
инструментами и intent-роутинг. Модель intent'а (`channel_analytics`) описана
в [ADR-008](adr/008-agentic-graph-rag.md#аналитика-поста-и-канала-числовой-контекст-а-не-текстовый-узел),
использует тот же классификатор, что заводится для пост-аналитики в
[Приоритете 1, Шаг 1.10](#шаг-110--intent-роутинг-на-аналитику-поста), с
третьим исходом вместо второго.

- [ ] Rule-based классификатор доводится до третьего исхода — `channel_analytics`
      (тот же классификатор, что заводится в Шаге 1.10, не новый).
- [ ] `GetChannelAnalytics(period)` — обёртка над `channel_metrics.build_channel_summary`
      + `build_channel_trend`.
- [ ] `GetTopPosts(period, limit)` — обёртка над `channel_metrics.build_top_posts`.
- [ ] `channel_analytics` intent обходит vector search и agentic-цикл целиком —
      вызов инструмента напрямую после классификации.

### Шаг 3.2 — Предпосылки для тональности комментариев (write-time)

- [ ] **Precomputed тональность комментариев** — классификация (правило /
      дешёвая модель / LLM) выполняется при синхронизации комментариев из
      Telegram (`comments_flow.py` / `comment_sync_pending.py`), результат
      сохраняется как поле на комментарии. Не в момент запроса.
- [ ] Стоимость пересчёта при backfill старых комментариев — отдельный вопрос
      проектирования (разовая миграция vs постепенный пересчёт).
- [ ] Место хранения — поле в JSON комментария на посте vs отдельная таблица
      (зависит от того, понадобятся ли по этому полю отдельные индексы/выборки).

### Шаг 3.3 — Инструмент ранжирования по тональности

Зависит от Шага 3.2 (нужно готовое precomputed поле).

- [ ] `RankPostsByNegativeComments(limit)` — прямой SQL `GROUP BY`/`ORDER BY` по
      precomputed `sentiment`, не vector search и не agentic-цикл.
- [ ] Общий принцип: агрегирующий вопрос → структурный SQL-запрос по
      precomputed полю, а не проход agentic-цикла по многим объектам.

### Связь с существующей аналитикой

Обе части приоритета — расширение уже существующего в продукте аналитического
контура (`backend/app/services/analytics/`): Шаг 3.1 использует его текущие
метрики (просмотры/репосты/реакции) как есть, Шаг 3.3 добавляет ещё одну
precomputed-метрику (тональность) поверх той же схемы — не новая архитектура.

### Критерий завершения этапа

- Пользователь может спросить «как растут просмотры канала» или «какие посты
  за месяц набрали больше всего» и получить ответ через готовые агрегаты, без
  прохода agentic-цикла и без vector search (Шаг 3.1, доступен раньше и
  независимо от Шагов 3.2–3.3).
- Пользователь может спросить «какие посты вызвали больше всего негатива в
  комментариях» и получить осмысленный ранжированный список без прохода
  agentic-цикла по каждому посту канала (Шаг 3.3).
- Агрегирующие и аналитические вопросы не расходуют бюджет
  `RAG_AGENT_MAX_STEPS` — они идут отдельным, более дешёвым путём (один
  SQL-запрос или прямой вызов инструмента).
