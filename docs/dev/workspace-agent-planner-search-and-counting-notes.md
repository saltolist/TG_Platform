# Workspace Agent: planner, semantic search и структурные подсчеты

**Дата:** 2026-07-20  
**Статус:** историческая диагностика; порядок реализации заменен единым планом
**Актуальный план:** [workspace-agent-unified-integrity-counting-plan.md](workspace-agent-unified-integrity-counting-plan.md)
**Проблемный чат:** `05623875-8e8c-468e-9187-5c6e8cf7b29b`  
**Проблемный run:** `9b077f6d-fec4-475d-be62-2cf2b0071fbc`

Этот документ сохраняется как описание симптомов, причин и acceptance-сценариев.
Он не является самостоятельным roadmap и не должен использоваться для создания
параллельного planner loop, resolver или context ledger.

## 1. Контекст

На вопрос «А сколько у меня заметок с изображениями?» Workspace Agent ответил,
что таких заметок нет. В действительности заметка
`464344bc-38e3-4c7b-be4c-3db81d9b4a7f` с названием «Варианты изображений для
поста» содержит два файла `image/png`. Правильный результат по текущим данным:

- заметок с изображениями: `1`;
- файлов-изображений в этой заметке: `2`.

Agent увидел название заметки в полном каталоге `/notes/`, но каталог содержал
только `id`, `title` и `parent_post`. Поля о файлах и изображениях отсутствовали.
При этом контракт хода был `coverage=complete`,
`evidence_granularity=catalog`, а `planner_calls_used=0`. Verifier признал сам
факт наличия каталога достаточным, после чего answer-модель интерпретировала
отсутствие сведений об изображениях как отсутствие изображений.

Это не ошибка vision: содержимое изображений не открывалось, а наличие файлов
не было передано в evidence.

## 2. Что не устраивает

1. Planner может вообще не вызываться для factual `read`-запроса, если seed и
   verifier формально считают evidence достаточным. В результате planner не
   получает возможности заметить, что для фактического критерия не хватает
   полей или глубины чтения.
2. Каталог объявлен достаточным для количества и наличия, но схема каталога не
   гарантирует наличие соответствующих атрибутов. «Поле не передано» сейчас
   может ошибочно трактоваться как `false` или `0`.
3. Подсчет общего размера каталога выполняет backend, но подсчет подмножества по
   условию часто остается answer-модели. Это ненадежно для больших списков,
   обрезанного контекста, повторяющихся объектов и нескольких уровней вложенности.
4. Для обязательного источника с `coverage=complete` semantic search полностью
   исключается. Это защищает полноту от top-k, но одновременно теряет полезные
   поисковые сигналы, точные фрагменты и приоритизацию кандидатов.
5. Термин «изображения в постах» неоднозначен: это могут быть прямые
   `post.media`, изображения в `post.notes[].files` или количество заметок поста,
   в которых есть изображения. Эти значения нельзя смешивать.
6. Текущий grader допускает отрицательное утверждение об изображениях, когда в
   evidence нет attachment-записей. Он не отличает доказанное отсутствие от
   отсутствия самого признака в evidence.

## 3. Почему текущий semantic search не решает подсчет

`SearchNodes` является top-k поиском по текстовым узлам и не предоставляет
надежный структурный фильтр `has_image=true` или `mime_type=image/*`.
`media_meta` в основном содержит имя файла. Такой поиск может найти полезного
кандидата, но не может доказать, что найдены все изображения, и не должен быть
основанием для точного или отрицательного ответа.

Для `coverage=complete` полный каталог уже содержит все `post_id` или `note_id`,
поэтому semantic search не увеличивает множество объектов этого корпуса. Он все
равно может дать прирост информации:

- добавить точные совпавшие фрагменты для уже известных объектов;
- ранжировать и приоритизировать full-text reads;
- обнаружить связанные объекты из optional-источников;
- показать, какие semantic cards требуют перепроверки по оригиналу.

Следовательно, semantic search должен быть аддитивным сигналом, а не заменой
авторитетного каталога и не способом сократить complete-множество.

## 4. Рабочие решения

Ниже зафиксировано направление, которое на данный момент считаем предпочтительным.
Это еще не разрешение на реализацию.

### 4.1 Planner для factual read

- Для каждого factual `read` должен существовать явный и проверяемый
  `plan decision`. Это не означает обязательный бессмысленный LLM-вызов для
  каждого запроса.
- LLM-planner должен вызываться, когда есть хотя бы одно из условий: semantic
  predicate, неоднозначность, несколько источников, выбор глубины чтения,
  незакрытый evidence gap или несколько допустимых стратегий.
- Для однозначного структурного запроса допустим deterministic fast path.
  Если LLM-planner всё же вызывается, `USE_FAST_PATH` должно быть явным
  решением с проверенным основанием, а не формальным «ничего не делать».
- Planner не может отменять требования контракта: `coverage=complete` остается
  жесткой runtime-гарантией и не может быть заменен top-k выдачей.
- Предпочтительный порядок для дальнейшего проектирования:
  `classifier/contract -> deterministic seed -> planner -> verifier -> answer`.

Planner не должен получать только неполный каталог и самостоятельно решать,
достаточно ли его. Перед вызовом verifier должен сформулировать typed gap,
например:

```text
required property: notes.has_images
evidence: catalog present, property absent
available actions: structural aggregate, open notes
```

Если инструмента, способного закрыть gap, нет, planner возвращает
`UNSUPPORTED_EVIDENCE_GAP` или `PARTIAL`, а не `FINISH_READY`.

Каждое действие planner должно иметь ожидаемый прирост evidence. После
исполнения verifier проверяет этот прирост; повторный planner-вызов разрешается
только при новом gap или новом evidence. Нужно измерять `planner_noop_rate` —
долю вызовов без нового evidence, изменения стратегии или обнаружения проблемы.

### 4.2 Аддитивный semantic search

- Для semantic-критериев (`«про пространственную систему»`, похожая тема,
  назначение объекта) semantic search может выполняться и при
  `coverage=complete`.
- Его результаты только обогащают, ранжируют и связывают полный каталог.
- Объекты, отсутствующие в top-k, не исключаются из complete coverage.
- Для чисто структурного запроса без semantic-критерия поиск может быть пропущен
  явным решением planner.

### 4.3 Детерминированные структурные подсчеты

- `has_image`, `file_count`, `image_count` и агрегаты по ним вычисляет backend,
  а не planner и не answer-модель.
- Для заметок должны отдельно возвращаться как минимум:
  `total_notes`, `notes_with_files`, `notes_with_images`, `image_files_total`.
- `notes_with_images` считается по уникальным заметкам, у которых есть хотя бы
  один файл с MIME `image/*`; оно не равно числу файлов-изображений.
- Структурный подсчет должен охватывать и глобальные заметки, и заметки внутри
  постов, с учетом видимости, tenant и статуса родительского поста.

### 4.4 Явная схема каталогов

- Атрибуты наличия должны быть обязательными и явными, включая нулевые значения:
  `file_count=0`, `image_count=0`, `has_images=false`.
- Отсутствующее поле означает `unknown/not_provided`, а не `0` или `false`.
- Каталог должен возвращать структурированные items и готовые агрегаты; текстовое
  представление остается только формой отображения evidence.
- Verifier должен проверять не только наличие `/notes/` или `/posts/`, но и то,
  что evidence предоставляет свойства, необходимые для критерия запроса.

### 4.5 Отдельные показатели для постов

Для поста не смешивать:

- `direct_media_count` и `direct_image_count` для `post.media`;
- `note_file_count` и `note_image_count` для файлов во всех заметках поста;
- `notes_with_files_count` и `notes_with_images_count` для количества заметок
  поста, удовлетворяющих условию.

Если пользователь говорит просто «посты с изображениями», контракт или planner
должен определить область по контексту либо явно разделить прямые изображения
поста и изображения в его заметках.

### 4.6 Проверяемый ответ

Для смысловых критериев LLM может определять принадлежность объекта к теме, но
ответ должен показывать итоговое множество, а не только число:

```text
Нашел 2 поста про пространственную систему:
- ...
- ...
```

Для структурных критериев итоговое множество и число формирует backend; LLM
только объясняет результат.

### 4.7 Когда вызов planner оправдан

Вызов оправдан, если planner может выбрать между несколькими реальными
стратегиями или закрыть явно обнаруженный пробел. Для запроса о заметках с
изображениями это означает: planner должен либо выбрать структурный агрегат,
либо инициировать чтение заметок, а затем получить проверяемый `image_count`/
`has_images`.

Вызов не считается полезным, если planner просто повторяет уже проверенный
fast path, не получает нового evidence и не меняет стратегию. Такой вызов можно
оставить только как наблюдаемый контрольный шаг, но его доля должна быть
измерена и ограничена.

## 5. Что пока не решено

- Нужен ли буквальный LLM-вызов для каждого `read`, включая точный unfiltered
  count. Рабочее предпочтение — обязательное plan decision для каждого
  factual `read`, а LLM-вызов только при semantic/predicate/multi-source,
  неоднозначности или evidence gap. Если будет выбран режим LLM-вызова всегда,
  необходимы `USE_FAST_PATH`, progress gate и метрики `planner_noop_rate`.
- Нужен ли новый универсальный `ListObjects(filters, aggregate)` или отдельные
  инструменты для заметок, постов и вложений.
- Должен ли structural predicate определяться classifier-ом, planner-ом или
  детерминированным contract compiler. Независимо от выбора результат должен
  проверяться verifier-ом.
- Какой объем complete-каталога и semantic cards допустим в интерактивном run;
  для больших корпусов потребуются paging, агрегаты и явный coverage state.
- Нужно ли включать semantic search для каждого complete semantic-запроса или
  дать planner возможность пропускать его, когда карточки всех объектов уже
  достаточны.

## 6. Ожидаемые acceptance-сценарии будущей реализации

1. «Сколько у меня заметок с изображениями?» возвращает `1` заметку и отдельно
   сообщает о `2` файлах-изображениях. Если image-поля отсутствуют, verifier
   создает typed evidence gap; planner закрывает его структурным агрегатом или
   чтением заметок, а отрицательный ответ без этого невозможен.
2. «Сколько у меня постов про пространственную систему?» рассматривает каждый
   актуальный пост, использует semantic search только как дополнительный сигнал
   и перечисляет посты, включенные в результат.
3. Trace factual `read` показывает явное решение planner либо документированный
   детерминированный fast path, выбранный согласно окончательной политике.
4. Semantic top-k никогда не уменьшает complete coverage set.
5. Backend-тесты проверяют различие между числом объектов с изображениями и
   числом файлов-изображений, включая изображения в заметках поста и прямые
   медиа поста.
6. Для каждого вызванного LLM-planner trace показывает ожидаемый gap/action и
   фактический прирост evidence; no-op вызовы считаются отдельно.
