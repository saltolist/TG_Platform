# ADR-008: Agentic Graph RAG — модель retrieval

## Статус
📝 Предложено (план; реализация — Фаза 2, шаг 6 и далее)

> Порядок и приоритет реализации (что первым, что вторым, что отложено) —
> в отдельном документе: [Роадмап: Agentic Graph RAG](../roadmap-agentic-rag.md).
> Здесь зафиксирована только модель — граф, каскад, инструменты, принципы.
> Конкретные примеры трассировки на разных запросах — в
> [Сценарий: Agentic Graph RAG на разных запросах](../agentic-rag-scenario.md).

## Контекст

Текущий RAG (Фаза 2, шаг 4) индексирует только **заметки** (`note_embeddings`,
`markdown_to_index_text`, `retrieve_top_k`, `format_rag_context` — см.
[phase-2-ai.md](../../backend/phases/phase-2-ai.md)). Посты, медиа постов и вложения
заметок (`attachment:<id>`) в retrieval не участвуют: `attachment:<id>` при
индексации вырезается, текст поста доступен AI только через bundle (шаг 3), и то
только в post chat.

Требования, которые нужно закрыть:

1. AI должен уметь при необходимости подтягивать **посты**, их **медиа** и
   **заметки** — не только в post chat, но и в global chat.
2. Из заметок при необходимости должны подтягиваться **вложенные файлы и медиа**
   (`note.files[]`), а из постов — их **заметки** (переход по связи пост → заметки).
3. Медиа и файлы должны подключаться **только когда это нужно для ответа**, а не
   всегда — иначе промпт раздувается, а vision/извлечение текста из файлов стоит
   денег и времени на каждый запрос.
4. Похожая логика должна закрыть потребность — AI читает **комментарии** поста
   по необходимости (это часть первого приоритета, наравне с постами и заметками
   — см. [роадмап](../roadmap-agentic-rag.md)).
5. Тяжёлый многошаговый retrieval (agentic) не должен вызываться на каждый запрос —
   только когда простой поиск не даёт ответа.

Отдельно зафиксирован **периметр** этого ADR: он описывает только модель
**retrieval** (agentic RAG, включая чтение комментариев) — какие узлы графа
существуют, как каскадируется поиск, каким набором инструментов агент может
пользоваться. Возможность AI **писать** — редактировать, откладывать, публиковать
посты, отвечать на комментарии — только упоминается здесь как мотивация для формы
решения (принцип read-tools vs write-tools), а порядок и объём реализации — в
[Роадмап: Agentic Graph RAG](../roadmap-agentic-rag.md).

## Рассмотренные варианты

**Тип RAG**
- A. Классический GraphRAG (Microsoft-style): извлечение сущностей из текста LLM,
  community detection, global/local search — избыточно для одного канала/аккаунта,
  где связи между постом, заметками, медиа и вложениями уже есть явно в JSONB.
- B. **(выбран)** Structured Graph RAG: граф — это уже существующая структура данных
  (`post.notes[]`, `note.files[]`, `post.media[]`), retrieval комбинирует vector
  search по тексту с обходом этих связей.
- C. Только flat vector search по всем узлам без графа — не решает переход
  «нашли пост → нужны его заметки → нужны файлы из заметки» без ручного склеивания
  на бэкенде при каждом новом типе связи.

**Момент подключения медиа/файлов**
- A. Индексировать и подтягивать бинарный контент (vision, OCR) при каждом
  запросе — дорого, большая часть запросов не касается медиа.
- B. Хранить только текстовые описания (alt/имя) без возможности заглянуть внутрь
  файла — не закрывает «прочитай отчёт из вложения».
- C. **(выбран)** Двухуровневая индексация: на **этапе записи** извлекать текст из
  файлов, где это дёшево (PDF/doc → text); на **этапе запроса** решать через
  planner, нужно ли подключать vision/бинарный контент, а не тащить всё по
  умолчанию.

**Управление стоимостью многошагового retrieval**
- A. Всегда полный agent loop (planner решает на каждом шаге) — надёжно находит
  вложенный контент, но добавляет 1–4 c и несколько LLM-вызовов на **каждый**
  запрос, включая тривиальные.
- B. Только одноуровневый vector search, без переходов по графу — быстро, но не
  закрывает cascading-сценарии («пост → его заметки → файл в заметке»).
- C. **(выбран)** Каскад: дешёвый плоский retrieval по умолчанию, agentic-обход
  графа — только при явной эскалации.

## Решение

### Два разных смысла «агентности»

Важно развести до деталей — модель ниже описывает **два разных вида** агентного
поведения, с разной степенью автономии:

| | Приоритет 1 (retrieval, этот ADR) | Приоритет 2 (действия, см. роадмап) |
|---|---|---|
| Что делает LLM | Многошаговое рассуждение: что и откуда вытащить для ответа | Распознаёт явную команду пользователя → формирует действие |
| Когда включается | По эскалации (не на каждое сообщение, см. [ниже](#когда-запускается-жизненный-цикл-запроса)) | Только при явной команде в конкретном сообщении |
| Автономность | Planner сам решает шаги и цели внутри своего цикла | Ноль автономности — только реакция на команду + обязательное подтверждение перед применением |
| Риск ошибки | Низкий (только чтение) | Высокий (реальный Telegram-канал) → жёсткий gate |

Этот ADR фиксирует только первую строку — retrieval-агент. Принцип для второй
строки закреплён в конце документа ([Принцип для будущих write-действий](#принцип-для-будущих-write-действий)),
детали — в роадмапе.

### Граф сущностей: вложенность, а не ссылки

Важная поправка к интуиции «граф = документы со ссылками друг на друга»: между
постом, его заметками, медиа и комментариями **нет ссылок** — это не отдельные
документы. Пост хранится как один JSONB-объект (`posts.data`), где `notes[]`,
`media[]`, `comments[]` — это **вложенные поля того же объекта**, а не отдельные
сущности, требующие перехода. Заметка внутри поста, в свою очередь, тоже хранит
`files[]` как вложенный массив внутри себя.

```
post (один JSONB-объект)
  ├─ text
  ├─ notes[]     ── note { title, body, files[] { id, name, url, type } }
  ├─ media[]     ── { name, url, type }
  └─ comments[]  ── { author, text, date }
```

Единственное место, где существует **настоящая текстовая ссылка** — `attachment:<id>`
внутри `note.body`, указывающая на конкретный элемент `note.files[]` **этой же
заметки** (нужна, чтобы понять, какой из нескольких файлов заметки относится к
конкретному фрагменту текста — не для того, чтобы обнаружить сам факт наличия
файлов, он уже известен структурно).

**Практическое следствие:** «обход графа» executor'ом — это не поиск ссылок в
тексте, а **бесплатное чтение соседних полей уже загруженного объекта**
(`len(post.notes)`, `len(post.media)`, `len(post.comments)`, `len(note.files)`).
Открыть пост (`OpenPost`) означает получить из Postgres **весь** JSONB одним
запросом — заметки, медиа, комментарии физически уже в памяти. «Инструменты»
(`ListPostNotes`, `ListPostComments`, …) не идут за данными — они решают, **что
из уже полученного включить в промпт** (вопрос токенового бюджета, не доступа).
Единственный шаг с реальной стоимостью fetch — открытие **содержимого**
вложения (`HydrateAttachment`, см. [ниже](#условная-гидратация-медиафайлов)), а
не факта его существования.

Отдельное хранилище рёбер не нужно, пока не появятся связи, которых нет в
текущих данных (например, перекрёстные ссылки между заметками или между постами).

Наличие `comments[]` в этой структуре — не отдельное решение, а часть той же
вложенности, что и `notes[]`/`media[]`; чтение комментариев через
`ListPostComments` входит в первую итерацию наравне с остальными (см.
[роадмап](../roadmap-agentic-rag.md), Приоритет 1). Откладывается только
**запись** — ответ на комментарии от AI, см.
[Отложено — ответ на комментарии](../roadmap-agentic-rag.md#отложено--ответ-на-комментарии).

### Индексация (запись)

Расширяется текущий `note_embeddings`-контур (pgvector) до общего индекса
текстовых узлов:

| Тип узла | Индексируемый текст | Источник |
|----------|---------------------|----------|
| `post_text` | текст поста | `post.data.text` |
| `note_chunk` | как сейчас (`markdown_to_index_text`) | `note.title` + `note.body` |
| `attachment_text` | извлечённый текст (PDF/doc) | `note.files[]`, где извлечение дёшево |
| `media_meta` | имя/alt/подпись (не бинарник) | `post.media[]`, `note.files[]` изображений |

Комментарии **не индексируются заранее** — они читаются агентом лениво в момент
запроса через `ListPostComments` (см. ниже), так как имеют смысл только в
контексте уже открытого поста, а не как самостоятельный retrieval-таргет. Это не
откладывает саму возможность чтения — только избавляет от отдельного
embedding-индекса под комментарии.

**Инвариант deleted-постов:** посты со `status: deleted` **не индексируются** и
**не участвуют в retrieval**. При soft-delete embeddings удаляются; при
восстановлении (`deleted` → `draft`) — переиндексируются. Draft / scheduled /
published индексируются как раньше.

### Cross-scope retrieval и bias

L1 и L2 `SearchNodes` используют единую политику пулов (`rag_retrieval_policy.py`):

| Чат | Пулы | Bias |
|-----|------|------|
| **global** | `scope=global` (заметки + `post_text`) + `scope=post` (`note_chunk`) | +boost к global |
| **post (X)** | локальные заметки поста X + global `note_chunk` + `post_text` любых постов | +boost к локальным заметкам поста X |

Заметки **других** постов в post-chat L1 **не ищутся** — только через L2
(`OpenPost` → `ListPostNotes`).

Параметр `RAG_SCOPE_BIAS` (по умолчанию `0.04`) — поправка к similarity для home
scope при merge результатов.

### Дополнительные fast-path эскалации L1 → L2

| Сигнал | Чат | Условие |
|--------|-----|---------|
| `cross_post` | post | L1 нашёл `post_text` **другого** поста |
| `post_note` | global | L1 нашёл `note_chunk` с `scope=post` |

Оба пропускают Tier B (цель известна) и сразу запускают L2 с seed/hint.

### Stop-evaluator в L2

Planner не может завершить цикл через `Stop`, пока детерминированный evaluator
(`rag_stop_evaluator.py`) не подтвердит, что открыт минимально нужный контекст
(заметка для «почему зашёл», комментарии для «что пишут», и т.д.). Паттерн
goal-based loop: проверяемый критерий завершения, а не слова planner'а.

### Когда запускается (жизненный цикл запроса)

Это не отдельный сервис и не фоновая задача — весь каскад выполняется
**синхронно, внутри существующего** `POST /ai/reply/`, в том же месте, где
сегодня уже вызывается `retrieve_rag_for_reply`, непосредственно **перед**
вызовом ответной LLM:

```
Пользователь отправляет сообщение (global или post chat)
   │
   ▼
резолв ключа AI-модели (BYOK / env / stub)
   │
   ├─ модель — заглушка ──────────────────────────► RAG не запускается
   ▼
модель реальная + RAG_ENABLED=1   ◄── существующий гейт, без изменений
   │
   ▼
L0 → L1 → sufficiency-check → (L2 по эскалации)
   │
   ▼
rag_context дописывается к последнему user-сообщению → ответная LLM → SSE
```

Предусловия (гейты) не меняются относительно сегодняшней реализации:
`RAG_ENABLED=1`, активна реальная (не stub) LLM-модель, резолвится
embedding-модель. Если хоть одно не выполнено — каскад не запускается вообще.

Частота по уровням внутри одной сессии чата — намеренно разная, в этом и смысл
каскада:

| Уровень | Частота |
|---|---|
| L0 (правила пропуска) | Каждое сообщение, прошедшее гейты — проверка в коде, без сети |
| L1 (плоский поиск) | Каждое сообщение, не отсеянное L0 — один embed + один SQL |
| Sufficiency-проверка, Ярус A | Сразу после каждого L1 — эвристики, без сети |
| Sufficiency-проверка, Ярус B | Почти каждое сообщение, кроме явного промаха/явной ссылки (fast-path Яруса A) — один дешёвый LLM-вызов |
| L2 (полный agentic-цикл) | Только по факту эскалации (промах, известная ссылка, или `sufficient: false` от Яруса B) — меньшинство сообщений |

Ручное управление для отладки/эксплуатации:

```env
RAG_MODE=auto   # off — не запускать вовсе
                # flat — всегда только L1, даже при сигналах эскалации
                # agentic — форсировать L2 всегда (для тестирования)
                # auto — каскад как описано выше (прод)
```

### Retrieval — трёхуровневый каскад

```
Запрос
   │
   ▼
[L0] Нужен ли RAG вообще?           правила, без LLM
   │  нет → сразу в LLM (bundle + история)
   ▼
[L1] Flat hybrid RAG (по умолчанию)  vector search по post_text + note_chunk
   │                                 + attachment_text, без обхода графа, без vision
   ▼
[Sufficiency-check] Хватает ли контекста для ответа? (см. ниже) — НЕ то же самое,
   │                 что «нашёл ли L1 хоть что-то похожее»
   ▼
[L2] Agentic RAG (по эскалации)      planner + tools, обход графа по одному hop за раз
```

**L0 — пропуск RAG.** Правила: реплики без предметного вопроса, правки
стиля/тона (уже в bundle), «перепиши покороче» в post chat (текст поста уже в
bundle).

**L1 — flat retrieval.** Прямое развитие текущего `retrieve_rag_for_reply`:
один embed запроса (с history-expansion и rewrite-on-miss, как сейчас) → vector
search по всем текстовым узлам → `format_rag_context`. Никакого обхода графа и
никакого vision на этом уровне.

**L2 — agentic retrieval.** Включается только при эскалации (см. ниже).
Ограниченный по шагам цикл planner/executor:

| Роль | Реализация |
|------|------------|
| Planner | `ragReasonerModels` (профиль), уже используется для rewrite-on-miss — расширяется до structured plan/tool-calls |
| Executor | детерминированный код, выполняет выбранный planner'ом инструмент |
| Answer LLM | обычная модель ответа (`llmModels`); получает уже собранный `rag_context`, как сегодня |

Инструменты executor'а (только чтение):

```
SearchNodes(scope, query, node_types)   # vector search по тексту
OpenPost(post_id)                       # текст + метаданные поста
ListPostNotes(post_id)                  # заголовки/сниппеты заметок поста
OpenNote(note_id)                       # тело заметки (chunk)
ListNoteAttachments(note_id)            # manifest файлов заметки (без бинарника)
HydrateAttachment(ref, mode)            # mode: metadata | text | vision
ListPostComments(post_id)               # комментарии поста, лениво по запросу
Stop(reason)
```

`OpenPost` не тянет автоматически заметки, медиа или комментарии — переход на
следующий hop (`ListPostNotes` / `ListNoteAttachments` / `ListPostComments` /
`HydrateAttachment`) делает planner отдельным шагом, только если решил, что это
нужно для ответа. Именно так решается «просмотреть заметки поста, который
добавили в обсуждение, и дальше по цепочке смотреть, нужны ли медиа или
комментарии».

Лимиты (защита от неконтролируемого цикла):

- `RAG_AGENT_MAX_STEPS` — максимум шагов обхода (по умолчанию 4);
- `RAG_AGENT_MAX_VISION` — максимум vision-гидратаций за запрос (по умолчанию 1);
- `visited: set(ref)` — каждый узел открывается не более одного раза за запрос.

Эти лимиты рассчитаны на единицы явно определяемых кандидатов (2–5), а не на
перебор всего канала — см. [границы модели](#границы-модели-что-agentic-rag-не-решает).

### Условия эскалации L1 → L2: проверка достаточности, а не только промах

Ключевой принцип: **успех L1 (высокая similarity, есть результат) не означает,
что контекста достаточно для ответа**. Пост может быть похож на вопрос по теме,
но содержать только анонс, а сами данные — лежать в заметке или вложении.
Поэтому эскалация проверяется **после каждого** L1-результата, а не только при
пустом ответе.

Первая версия модели пыталась развести это на два яруса — «дешёвые эвристики»
и «LLM-проверка только если эвристики неоднозначны». От этого пришлось
отказаться: критерий «эвристики неоднозначны» сам является ещё одной
эвристикой без явного правила, то есть двумя независимыми точками, где
проверка может **ложноотрицательно** не сработать — heuristics могут не
покрыть случай, а гейт «звать ли LLM» полагается на те же heuristics, чтобы
понять, что случай вообще странный. Пример пропуска: чанк не короткий, цифры
в нём есть, но не те, что нужны для ответа — ни один из сигналов ниже не
срабатывает, и старая модель молча объявляла «достаточно», не дойдя до LLM.

**Ярус A — эвристики, без LLM, выполняются всегда.** Роль изменилась: это не
гейт, решающий «звать ли Ярус B», а **fast-path для двух случаев, где ответ уже
известен без LLM**, плюс источник признаков для Яруса B во всех остальных:

1. **Промах** — пустой результат или `max similarity < RAG_ESCALATE_MIN_SIMILARITY`
   после rewrite-on-miss (тот же механизм, что уже есть в `rag_query.py`).
   Эскалация обязательна, Ярус B не вызывается — оценивать нечего, содержимого
   нет.
2. **Непройденный сосед с прямой ссылкой в самом чанке** — `attachment:<id>`
   вырезается из текста при индексации (`markdown_to_index_text`), поэтому в
   самом эмбеддинге его нет. Чтобы сигнал был доступен, id извлекаются отдельным
   regex-проходом по **сырому** `note.body` до зачистки и сохраняются рядом с
   чанком как метаданные (`referenced_attachment_ids`), не как часть
   индексируемого текста. Если у топ-чанка заметки есть такой id, а
   соответствующего `attachment_text` нет среди результатов L1 — эскалация с уже
   известной целью (сразу `HydrateAttachment(<id>)`, без отдельного шага поиска).
   Ярус B тоже не вызывается — цель уже известна, спрашивать LLM «нужно ли»
   бессмысленно. Пример трассировки —
   [Сценарий 3](../agentic-rag-scenario.md#сценарий-3--успешный-l1-но-контекста-недостаточно-прямая-ссылка-в-чанке).
3. **Текстовые маркеры-указатели** в самом чанке (regex: «см.», «подробнее в»,
   «результаты в файле», «полная таблица — в заметке» и т.п.).
4. **Несоответствие типа ожидаемого ответа контенту чанка** — грубая классификация
   вопроса по ключевым словам («сколько», «какой процент», «цифры» → ожидаются
   числа; «покажи», «график», «скриншот» → визуальный контент; «что пишут»,
   «комментари» → комментарии) против фактического содержимого найденного чанка.
5. **Чанк слишком короткий/общий** относительно среднего размера — похоже на
   заголовок/анонс, а не на содержательный ответ.
6. **Follow-up по истории**: запрос ссылается на ранее открытый узел («а на
   картинке?», «а во втором вложении?»), которого нет в текущем `rag_context`.

Сигналы 3–6 **больше не эскалируют напрямую** — они превращаются в булевы
признаки (`pointer_phrase`, `answer_type_mismatch`, `chunk_too_short`,
`is_followup`), которые передаются в Ярус B как часть входа, а не заменяют его.

**Ярус B — дешёвая проверка через reasoner, вызывается всегда, кроме двух
fast-path случаев выше** (сигналы 1 и 2). Это и есть «отдельный вызов LLM,
решающий, нужен ли L2» — только опирающийся на уже посчитанные признаки, а не
принимающий решение с нуля по сырому тексту. `ragReasonerModels` получает
короткий вход — вопрос, сам найденный чанк, булевы признаки сигналов 3–6 и
**манифест** непройденных структурных соседей (только `type` + `id` +
заголовок/имя, без содержимого — тот самый бесплатный manifest из
[графа сущностей](#граф-сущностей-вложенность-а-не-ссылки)):

```json
// вход: признаки Яруса A + манифест соседей, не их содержимое
{
  "signals": {
    "pointer_phrase": false,
    "answer_type_mismatch": true,
    "chunk_too_short": false,
    "is_followup": false
  },
  "neighbors": { "notes": [{"id": "n1", "title": "Черновик разбора"}], "media": [], "comments_count": 5 }
}
```

```json
// выход reasoner'а, structured
{ "sufficient": false, "open_next": ["note:n1"] }
```

Если `sufficient: false` — эскалация в L2, причём planner стартует сразу с
`open_next`, если он есть, а не с поиска с нуля. Это тот же `ragReasonerModels`,
что уже используется для rewrite-on-miss — задача дешёвая (маленький контекст,
бинарная классификация, а не генерация), может выполняться быстрой/дешёвой
моделью.

**Явный компромисс по стоимости:** в отличие от исходной версии («не платить
LLM-вызовом на каждый запрос»), эта модель вызывает Ярус B почти на каждое
RAG-сообщение (кроме явного промаха и явной ссылки) — то есть на большинство
сообщений, дошедших до L1. Это осознанный выбор в пользу меньшего числа
пропущенных эскалаций ценой одного дешёвого LLM-вызова там, где раньше не было
вызова вообще. Стоимость сопоставима с уже существующим rewrite-on-miss
(короткий контекст, structured-output), а не с полным L2-циклом.

Конфигурация:

```env
RAG_AGENT_MAX_STEPS=4
RAG_AGENT_MAX_VISION=1
RAG_ESCALATE_MIN_SIMILARITY=0.72
RAG_ESCALATE_ON_MISS=true
```

### Комментарии поста — read-only tool, а не отдельный индекс

Комментарии уже хранятся на посте (`post.data.comments`, синхронизируются с
Telegram — `comments_flow.py`) — как и заметки с медиа, это вложенное поле того
же JSONB-объекта, а не отдельный документ. Доступ к ним через
`ListPostComments(post_id)` внутри agentic-цикла (L2) — не через отдельный
предварительный embedding-индекс, а просто чтение уже загруженного поля из
`OpenPost`. Комментарии осмысленны только в контексте уже открытого поста,
поэтому предзаполнять по ним отдельный индекс не нужно. Это закрывает «AI
должен уметь читать комментарии при необходимости» без усложнения индексации.
Откладывается только **ответ** на комментарии от AI — это write-действие, см.
[роадмап](../roadmap-agentic-rag.md#отложено--ответ-на-комментарии).

### Аналитика поста и канала — числовой контекст, а не текстовый узел

Просмотры/реакции/комментарии/ER поста и канала уже посчитаны и хранятся
(`PostMetricSnapshot` / `ChannelMetricSnapshot`, `backend/app/services/analytics/`,
регулярный snapshot-cron). В отличие от текста заметок/постов это **не задача
similarity search** — у вопроса «сколько просмотров у поста» нет эмбеддинга, с
которым можно было бы сравнивать текстовые чанки. Поэтому аналитика не
подключается через обычную эскалацию L1 → sufficiency-check → L2, а
определяется **отдельной intent-классификацией до эмбеддинга вопроса**.

**Классификация intent'а (правило, без LLM и без vector search):**

| Intent | Признаки (ключевые слова/паттерны) | Маршрут |
|---|---|---|
| `content` (по умолчанию) | всё, что не попало в два intent'а ниже | обычный каскад L0 → L1 → sufficiency-check → L2 |
| `post_analytics` | просмотры, охват, реакции, ER, вовлечённость, «как зашёл пост», «сколько комментариев за неделю» | `GetPostAnalytics`, см. ниже |
| `channel_analytics` | то же, но без привязки к конкретному посту: «как растёт канал», «топ постов за месяц», «какой пост выстрелил» | [Приоритет 3](../roadmap-agentic-rag.md#приоритет-3--аналитические-агрегирующие-запросы), `GetChannelAnalytics`/`GetTopPosts` |

**`post_analytics` — новый read-tool Приоритета 1:**

```
GetPostAnalytics(post_id, period)   # обёртка над post_metrics.build_post_trend
```

- **Post chat** — `post_id` уже известен из контекста чата → тул вызывается
  сразу, минуя L0/L1/L2 текстового каскада для этого сообщения целиком
  (аналогично сегодняшнему правилу L0 «правки стиля — сразу в LLM», только
  результат — вызов инструмента, а не пропуск RAG).
- **Global chat** — если пост назван описательно («пост про скидки»), сначала
  нужно определить `post_id` обычным путём (`SearchNodes`/L1 по содержимому);
  `GetPostAnalytics` вызывается как обычный L2-шаг **после** идентификации
  поста, а не вместо каскада.
- Период (`period`) берётся из формулировки вопроса («за неделю» → `7d`) с
  фолбэком на дефолт аналитики (`30d`), по тем же значениям, что уже
  использует `channel_metrics.VALID_PERIODS`.

**`channel_analytics` — попадает в [Приоритет 3](../roadmap-agentic-rag.md#приоритет-3--аналитические-агрегирующие-запросы),**
так как это агрегация по всему каналу, а не деталь одного объекта. В отличие
от примера с тональностью комментариев в том же приоритете, здесь **precompute
уже существует** — снятие `ChannelMetricSnapshot` уже работает
(`analytics_snapshot.py`); задача сводится к обёртке готовых функций
(`build_channel_summary`, `build_channel_trend`, `build_top_posts`)
инструментами и к intent-роутингу, без нового этапа записи.

Итог: аналитика — это третий маршрут для входящего сообщения, наравне с
«обычный текстовый вопрос», выбираемый **до** того, как считается embedding
вопроса, а не после неудачной текстовой эскалации.

### Условная гидратация медиа/файлов

Медиа и вложения не попадают в промпт по умолчанию. `HydrateAttachment(ref, mode)`
вызывается planner'ом только когда это оправдано вопросом. Важно разделять
**бесплатный структурный доступ** (метаданные, текст заметок/комментариев — уже
в памяти, см. [граф сущностей](#граф-сущностей-вложенность-а-не-ссылки)) и
**реально платную операцию** — это только открытие *содержимого* вложения:

| mode | Когда | Механика | Стоимость |
|------|-------|----------|-----------|
| `metadata` | Достаточно имени/типа | Уже в JSONB | Бесплатно |
| `text` | PDF/doc, вопрос про содержимое | См. ниже | Обычно бесплатно (write-time) |
| `vision` | Картинка/график, вопрос про визуальный контент | `visionModels` из профиля | Всегда реальный вызов |

**`text` — два пути:**
1. **Write-time (по умолчанию, предпочтительный)** — текст извлекается из
   PDF/doc **при сохранении заметки**, той же durable-очередью, что уже
   используется для индексации заметок (`rag_worker.py`, `embedding_jobs`).
   В момент запроса `HydrateAttachment(mode="text")` — это просто `SELECT`
   уже готового `attachment_text`, без сети и без задержки.
2. **Lazy fallback** — если write-time извлечение ещё не прошло (например,
   backfill не выполнен): гидратация скачивает файл по `url` из MinIO,
   извлекает текст той же функцией и **сразу кэширует** результат обратно в
   `attachment_text` — повторный запрос к этому же файлу уже пойдёт по пути 1.
   Стоимость разовая на файл, не на запрос.

**`vision` — всегда реальная стоимость**, дешёвого пути нет: картинку нельзя
превратить в текст без вызова vision-модели. Контроль стоимости:
- **Лимит** `RAG_AGENT_MAX_VISION` — гидратируется не «все медиа поста», а
  только те 1–2, что planner явно выбрал по манифесту;
- **Кэш по хэшу содержимого файла** (не по `url`, он может смениться) — повторный
  вопрос про ту же картинку в другом чате не вызывает vision повторно, это
  дешёвый lookup, аналогично `attachment_text`;
- Файл, уже найденный через `attachment_text` в L1, не гидратируется повторно
  как `vision` — это предотвращает дублирование контекста.

Опционально на будущее (не обязательно для первой версии): дешёвый
auto-captioning картинок на этапе записи, чтобы такие изображения находились
уже в L1 по тексту описания — компромисс между стоимостью индексации и
полнотой поиска, отдельное решение вне рамок этого ADR.

### Отказоустойчивость при недостаточном контексте

Agentic-цикл всегда завершается одним из трёх способов, и ни один не должен
ронять запрос целиком:

1. **Planner решил `sufficient: true`** — штатное завершение.
2. **Исчерпан лимит** (`RAG_AGENT_MAX_STEPS` / `RAG_AGENT_MAX_VISION`) — цикл
   принудительно останавливается с тем контекстом, что успели собрать, даже
   если он неполный.
3. **Гидратация упала технически** (файл не скачался, vision-провайдер вернул
   ошибку, нет ключа для vision-модели) — источник пропускается, ошибка
   логируется (`logger.warning`), цикл продолжается с тем, что есть — по
   аналогии с уже существующим паттерном обработки сбоев RAG в `ai.py`
   (`try/except` вокруг `retrieve_rag_for_reply`, без падения всего ответа).

Подстраховка на уровне **ответной модели**, а не retrieval: system prompt
обязан явно требовать не придумывать факты/цифры, если их нет в переданном
контексте, а прямо сообщать, что не найдено. Это не решает поиск, но не даёт
системе выдать уверенную галлюцинацию вместо честного «не нашёл».

Более амбициозный вариант — явный уточняющий вопрос пользователю вместо тихого
«не нашёл» — не решён в этом ADR, рассматривается как возможное развитие UX
диалога отдельно от retrieval-архитектуры.

### Границы модели: что agentic RAG не решает

Модель выше спроектирована для одного класса вопросов — **«найди релевантное
(один объект или несколько явно определяемых кандидатов) и раскрой связанные с
ним детали»** (пост → его заметки → их вложения/комментарии). Важно явно
зафиксировать, что она **не решает**:

1. **Агрегация/ранжирование по всему корпусу** — «посты с самыми негативными
   комментариями», «сколько раз упоминали X», «средняя вовлечённость за
   месяц». Vector search (`SearchNodes`) возвращает top-k **похожих по смыслу**
   на текст запроса — это принципиально другая операция, чем «пройти по всем
   постам, посчитать метрику по каждому и отсортировать» (`GROUP BY`/`ORDER BY`).
   У «негативности комментариев» нет текста, с которым можно было бы сравнить
   embedding запроса — это вычисляемый признак, а не семантическое сходство.
2. **Массовый обход множества объектов** — даже без агрегации, «разбери каждый
   пост за март» при нескольких десятках постов не помещается в
   `RAG_AGENT_MAX_STEPS` (по умолчанию 4). Бюджет L2 рассчитан на единицы шагов
   с явно определяемыми кандидатами (2–5), а не на перебор всего канала.
3. Оба случая требуют **отдельного класса инструментов** — не расширения
   `SearchNodes`/graph-hop, а precomputed структурных метрик (посчитанных
   заранее, на write-time) + SQL-агрегации поверх них, по той же схеме, что уже
   применяется в продукте для числовой аналитики постов (просмотры/репосты/
   реакции — `backend/app/services/analytics/`). Это направление зафиксировано
   отдельно в
   [роадмапе — Приоритет 3](../roadmap-agentic-rag.md#приоритет-3--аналитические-агрегирующие-запросы),
   вне периметра этого ADR: здесь оно только очерчено как явная граница модели
   retrieval, чтобы не создавать ложных ожиданий, будто agentic-цикл решит и
   такие вопросы тоже.

## Последствия

- Индекс `note_embeddings` расширяется до общего индекса текстовых узлов (посты,
  заметки, извлечённый текст вложений); миграция и обратная совместимость —
  предмет отдельного шага реализации (Фаза 2, шаг 6).
- `retrieve_rag_for_reply` остаётся точкой входа для L1; L2 — новый модуль
  (`rag_agent.py` / `rag_tools.py` / `rag_graph.py`), подключаемый по каскаду, а не
  замена существующего кода.
- Большинство запросов проходят L0/L1/Ярус B и не платят задержку agentic-цикла;
  L2 добавляет заметную латентность (~1–4 c) только когда Ярус B вернул
  `sufficient: false` или сработал fast-path Яруса A (промах/известная ссылка).
- Почти каждое RAG-сообщение теперь платит один дешёвый LLM-вызов (Ярус B),
  а не только доля сообщений, как в первой версии модели — осознанный
  компромисс между латентностью (~0.2–0.5 c на короткий structured-запрос) и
  риском пропущенной эскалации.
- `ragReasonerModels` из профиля AI получает вторую и третью роли — rewrite
  запроса, Ярус B sufficiency-проверка, planner для agentic-цикла; в аккаунтах
  без настроенной RAG Reasoner-модели Ярус B и L2 недоступны, работает только
  L1 + fast-path Яруса A (сигналы 1–2), без сигналов 3–6 и без LLM-проверки
  остального — degraded, но не падающий режим.
- Комментарии не требуют отдельного embedding-индекса — читаются on-demand внутри
  agentic-цикла, что проще эксплуатационно (меньше данных для переиндексации при
  правках комментариев).
- Эскалация строится как проверка достаточности через Ярус B почти всегда, а
  Ярус A выполняет роль fast-path (два случая с уже известным ответом) и
  источника признаков для Яруса B, а не отдельного гейта «нужен ли LLM-вызов» —
  это устраняет риск двойного ложноотрицательного пропуска эскалации, но
  требует хранить рядом с чанком список referenced-`attachment:<id>` (для
  сигнала 2) и подключить манифест структурных соседей и признаки 3–6 к
  вызову reasoner'а (Ярус B).
- Гидратация текста вложений в норме бесплатна в момент запроса (write-time
  extraction через ту же очередь, что и индексация заметок); vision — всегда
  реальная стоимость, требует кэша по хэшу файла и строгого лимита на запрос.
- Сбой гидратации или исчерпание лимита не должны прерывать запрос — только
  сокращать собранный контекст (fail-soft), с финальной подстраховкой в system
  prompt ответной модели против галлюцинаций при неполном контексте.

## Принцип для будущих write-действий

Эта модель описывает только retrieval, но задаёт форму решения на будущее —
когда в роадмапе дойдёт очередь до записи (правка/отложить/опубликовать пост,
возможный ответ на комментарии): **retrieval-инструменты agentic RAG вызываются
planner'ом автономно** (это его работа — решать, что почитать для ответа);
**любой write-tool вызывается только по явной команде пользователя в сообщении и
требует подтверждения перед фактическим применением** — платформа управляет
реальным Telegram-каналом, и случайная автономная публикация/правка недопустима.
Действия синхронизации с Telegram (`publish_flow.py`, `comments_flow.py`) уже
существуют — будущие write-tools станут тонкой обвязкой поверх них, а не новой
логикой публикации. Порядок и объём реализации write-действий — в
[Роадмап: Agentic Graph RAG](../roadmap-agentic-rag.md).
